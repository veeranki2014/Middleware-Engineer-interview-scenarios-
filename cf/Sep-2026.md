## Difference between Fixpack and Refresh pack

Fixes for WebSphere software are delivered in the form of maintenance packages. There are three different types of maintenance packages:

- **Refresh pack**: A refresh pack is a cumulative set of fixes delivered together in a single maintenance package. Refresh packs may contain new function as well as fixes for known problems. After applying a refresh pack, the third digit in level of the product is changed. For example, if you have V6.0.0.1 installed and you install refresh pack 2 for V6, the product version changes to 6.0.2.0.

- **Fix pack**: A fix pack is a cumulative set of fixes delivered together in a single maintenance package. Fix packs contain only fixes for known problems. After applying a fix pack, the fourth digit in the level of the product is changed. For example, if you have V6.0.2.0 installed and you install fix pack 17 for V6.0.2, the product version changes to 6.0.2.17.

- **Interim fix (iFix)**: An interim fix is a fix for a specific problem for a specific level or levels or the product. An iFix is not a cumulative set of fixes. When the iFix is built, the levels of the product the iFix is for are set and the iFix will not install on any other levels. Interim fixes are included in the next possible fix pack after the interim fix is released.

### So, what is a fix pack?

A fix pack contains fixes for numerous issues. Fix pack with a higher version has all the fixes addressed by a fix pack with a lower version. So it is enough if we install a fix pack with the highest version. Fix packs can be downloaded from the Fix Central. Fix Central is the channel through which IBM provides fixes and updates for all its products.

### What is the Fix Pack Naming Convention?

`<V.R.M.F> – <Product> – <Optional Platform> – <MDV indicator><APAR number>.zip`

Eg: `8.0.0.1-WS-WCGWAS7-IFPM72441.zip`

- V – Version
- R – Release
- M – Modification Number
- F – Fix Level

Codes:
- IF – Interim Fix
- FP – Fix Pack
- MR – Manufacturing Refresh
- MDV – Maintenance Delivery Vehicle.

### Key Concepts

- **Software Updates**: These are changes made to a software product after its initial release. Updates can include bug fixes, security patches, performance improvements, and new features.
- **Cumulative**: In the context of cumulative fixes, it means that each new update contains all the fixes from previous updates. For example, if you have Update 2, it includes all the fixes from Update 1 as well.
- **Fixes**: These are modifications to the software's code intended to resolve specific issues or problems, such as software crashes, incorrect behavior, or security vulnerabilities.

## Why do we need a Webserver if there is no static content?

Even without static content, a web server (Apache/IHS/Nginx) is used for:

- Reverse proxy: load balancing requests to app servers (via plugins like the WebSphere plugin, mod_wl for WebLogic).
- SSL termination: offloading so app servers don't handle raw TLS.
- Session affinity (sticky sessions) routing to the correct app server.
- Security layer — hides app server topology, can apply WAF rules, IP filtering.
- Virtual hosting — multiple domains/URLs routed from one entry point.

## Difference between Apache vs Nginx

Apache uses a process/thread-per-connection model whereas Nginx uses an event-driven, non-blocking architecture a small number of worker processes handle thousands of connection concurrently.

Apache webserver is vendor certified plugin for legacy enterprise stacks like WebSphere, WebLogic. Nginx is basically suitable for cloud-native, containerized or high-concurrency workloads.

Nginx handles the outer edge because its efficient at scale. Apache and IHS sit closer to the application server

## Configuration for multiple URLs and virtual hosts

**Apache (httpd.conf / vhosts.conf):**

Use mod_proxy/mod_weblogic (WebLogic Proxy Plugin) or mod_jk/IBM HTTP plugin (plugin-cfg.xml) for WebSphere.

```apache
<VirtualHost *:443>
    ServerName app1.example.com
    SSLEngine on
    SSLCertificateFile /etc/pki/tls/certs/app1.crt
    SSLCertificateKeyFile /etc/pki/tls/private/app1.key
    ProxyPass /app1 http://weblogic_cluster/app1
    ProxyPassReverse /app1 http://weblogic_cluster/app1
</VirtualHost>
```

**Nginx:**

Different URLs are handled via distinct server_name/VirtualHost blocks or location/Location path-based routing to different backend clusters.

```nginx
server {
    listen 443 ssl;
    server_name app2.example.com;
    ssl_certificate /etc/nginx/certs/app2.crt;
    ssl_certificate_key /etc/nginx/certs/app2.key;

    location /app2 {
        proxy_pass http://weblogic_upstream;
    }
}
```

## Disaster Recovery Design

**RTO** (Recovery Time Objective) - How long the application can be down? Is that 15 mins/1hr/ 4 hrs.

**RPO** (Recovery Point Objective) - How much data can we lose? Is that 0/ 5 min/ 1 hr

Based on the RTO and RPO numbers dictate whether we need active-active or active-standby.

### Cutover Decision Matrix

| Scenario | Cutover Decision |
|---|---|
| Full EAST1 region outage | YES, Full cutover because no choice, its complete unavailability. |
| App server failure, but infra healthy | Usually NO - Fix in place. |
| Database Primary failure | Yes if DB is unrecoverable within the RTO |
| Security Incident in EAST1 | YES, isolate and cutover |
| Planned maintenance | YES, planned cutover |

### Failover Runbook Skeleton

```
1. DECLARE DISASTER
   - Incident commander confirms East1 is non-recoverable within RTO
   - Formal DR declaration (not ad-hoc — needs sign-off per change mgmt)

2. FREEZE EAST1 WRITES (if partially up)
   - Prevent further data divergence

3. PROMOTE EAST2 DATABASE
   - Data Guard: SWITCHOVER (planned) or FAILOVER (unplanned)
   - DB2 HADR: TAKEOVER HADR command

4. VALIDATE EAST2 WAS CELL
   - serverStatus.sh -all across East2 cell
   - Confirm app version parity with East1's last known good deployment

5. REPOINT MQ / MESSAGING
   - Activate East2 queue managers, redirect channels

6. FLIP GSLB/DNS WEIGHT
   - Shift traffic weight East1:East2 from 100:0 → 0:100
   - Lower TTL beforehand if possible during planned events

7. VALIDATE END-TO-END
   - Synthetic transactions through full stack (proxy → WAS → DB → MQ)
   - Check SystemOut.log, DB connectivity, session behavior

8. COMMUNICATE
   - Status page update, stakeholder notification

9. POST-INCIDENT
   - Once East1 recovers, re-sync East1 as new standby (don't just flip back —
     re-establish replication direction East2 → East1 first, THEN failback)
```
